# DramaFlow Studio PRD v1.0

## 1. 产品概述

### 1.1 产品名称

- 暂定名：`DramaFlow Studio`

### 1.2 产品定位

- 一个运行在本机的 `local-first` AI 短剧生产平台。
- 面向短剧创作者、小型工作室、AI 漫剧团队，提供从故事开发到成片交付的完整工作流。
- 核心目标不是“一键生成整部短剧”，而是把短剧生产拆成可确认、可重跑、可审查、可复用的工业流程。

### 1.3 参考母本

- `drama-skills`
  - 提供 creator-first 工作流骨架
  - 提供五份核心文档思路
  - 提供先确认后生产的方法论
- `short-drama`
  - 提供剧情规则体系
  - 提供题材模板、钩子、节奏、审查逻辑
- `CineGen-ShortDrama`
  - 提供 Script-to-Asset-to-Keyframe 思路
  - 提供导演工作台和关键帧驱动方法
- `huobao-drama`
  - 提供多模型接入、任务编排、媒体处理与导出思路
- `trae_projects`
  - 仅参考模型调用与 adapter 分层方式
  - 不沿用其双源状态、补丁式 prompt 和高耦合结构

### 1.4 参考采用策略

- 我们参考外部项目的优先级是：
  1. 方法论
  2. 工作流结构
  3. 领域模型与 contract
  4. 最后才考虑少量代码
- 默认策略是 `重写实现`，不是直接拼装外部仓库代码。
- 参考项目主要用于回答：
  - 工作流该如何分阶段
  - 关键数据边界该如何建模
  - prompt 与任务系统该如何解耦
- 参考项目不用于：
  - 直接复制页面结构
  - 直接复制 prompt 文本
  - 直接复制题材模板和内容资产
  - 直接复制原项目的历史兼容逻辑
- 具体采用策略见：
  - `reference-adoption-policy-v1.md`

## 2. 核心问题

- 现有 AI 工具通常只强在生成，不强在生产管理。
- 故事、设定、分镜、提示词经常不是同一套真相源，导致返工成本高。
- 角色一致性、服装 continuity、镜头 handoff 缺少结构化约束，只能依赖长 prompt 硬撑。
- 视频生成质量波动大，本质上是“事实层不稳”而不是“模型本身太差”。
- 系统容易越做越难维护，因为业务真相、模型调用、UI 补丁、任务状态混在一起。

## 3. 产品目标

### 3.1 V1 目标

- 建立本机运行的短剧工作台。
- 打通从项目初始化到单集分镜确认的创作闭环。
- 建立角色、服装、场景、道具、镜头的统一台账体系。
- 建立统一 Prompt 编译器，禁止多处拼接 prompt。
- 建立统一任务系统，支持图片、视频、TTS、合成的可重跑执行。
- 建立基础审查系统，能发现剧情、设定、continuity、合规问题。

### 3.2 非目标

- 不在 V1 直接做多租户 SaaS。
- 不在 V1 直接做复杂权限系统。
- 不在 V1 直接做支付、套餐、计费。
- 不在 V1 直接做高级剪辑、自动特效和音乐编排。
- 不承诺全自动无人工确认成片。

## 4. 目标用户

### 4.1 个人创作者

- 有故事点子、小说素材或短剧想法。
- 需要快速搭建故事结构和镜头规划。
- 希望减少 prompt 试错。

### 4.2 小型工作室

- 有稳定短剧产能需求。
- 需要统一资产台账和镜头 continuity。
- 需要支持批量生产和失败重跑。

### 4.3 编导小团队

- 需要围绕统一项目资产协作。
- 需要让故事、设定、分镜、生产有清晰交接边界。

## 5. 产品价值

- `写得稳`
  - 通过故事规则引擎控制题材、钩子、节奏、角色弧光。
- `镜头稳`
  - 通过关键帧驱动减少视频镜头漂移。
- `角色稳`
  - 通过角色、服装、场景、道具台账控制一致性。
- `生产稳`
  - 通过统一任务系统管理生成、重试、回填和导出。
- `维护稳`
  - 通过单一真相源和模块边界降低系统复杂度。

## 6. 产品形态

### 6.1 运行方式

- 前端工作台运行在本地浏览器。
- 本地服务负责数据管理、任务执行、文件读写、FFmpeg 合成。
- 图片、视频、LLM、TTS 通过云端模型 API 调用。
- 项目数据、产物、日志和缓存优先保存在本机。

### 6.2 形态判断

- 不是纯 SaaS。
- 不是纯离线软件。
- 是 `本机工作台 + 本地执行层 + 云端模型能力` 的混合结构。

## 7. 核心工作流

1. 项目初始化
2. 故事开发
3. 设定沉淀
4. 剧本与分镜
5. Prompt 编译
6. 生产执行
7. 审查修订
8. 导出交付

### 7.1 项目初始化

- 设置题材、受众、语言、画幅、单集时长、总集数。
- 确定项目级风格方向和生产目标。

### 7.2 故事开发

- 生成故事骨架。
- 生成角色关系。
- 生成分集地图。
- 规划节奏、钩子、反派体系。

### 7.3 设定沉淀

- 建立角色台账。
- 建立服装与外观版本。
- 建立场景和道具台账。
- 建立视觉风格规则。

### 7.4 剧本与分镜

- 按集、场、镜组织内容。
- 为每个镜头定义意图、构图、运镜、表演说明。
- 为关键镜头建立 start / end / key frame 规格。

### 7.5 Prompt 编译

- 从故事、设定、分镜三层事实统一编译 prompt。
- 输出图片 prompt、视频 prompt、TTS 文本。
- 支持 diff、确认、版本管理。

### 7.6 生产执行

- 创建图片、视频、TTS、合成任务。
- 通过任务系统统一执行和回调。
- 支持失败重试和局部重跑。

### 7.7 审查修订

- 审查剧情逻辑。
- 审查角色与场景 continuity。
- 审查 prompt 质量。
- 审查合规风险。

### 7.8 导出交付

- 导出剧本文本。
- 导出素材包。
- 导出镜头包。
- 导出成片或中间交付包。

## 10. 关键产品约束

- 故事、设定、分镜必须是唯一真相源。
- UI 不允许直接拼 prompt。
- Adapter 不允许二次改写业务 prompt。
- 任务系统是唯一模型调用入口。
- 生成失败不能反向污染故事、设定、分镜事实。
- 审查结论必须结构化，不允许只留散乱日志。
- 外部参考项目默认只借方法和结构，不直接复制实现。
- 所有外部代码级复用都必须经过 License 与边界核验。

## 11. V1 成功指标

- 从立项到首集分镜确认的平均耗时。
- 单镜头重跑率。
- 角色一致性问题率。
- prompt 确认后的一次通过率。
- 单集交付耗时。
- 单集平均成本。
- 审查问题关闭率。

## 14. 一句话结论

- `DramaFlow Studio` 的本质不是“生成器”，而是一个以故事真相源为核心、以关键帧为桥梁、以任务系统为执行底座的本地短剧生产工作台。
