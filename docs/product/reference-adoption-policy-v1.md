# Reference Adoption Policy v1.0

## 1. 文档目的

本文档用于定义：

- 我们如何参考外部短剧项目
- 我们借用哪些思想、结构和 contract
- 我们明确不借用哪些实现和内容资产
- 我们在代码复用、License 和商业化上的边界

该文档的目标不是限制参考，而是防止后续实现重新落回：

- 直接复制代码
- 复制现成 prompt 文本
- 复制题材模板资产
- 混入外部仓库的历史耦合

## 2. 总体原则

### 2.1 先借方法，再借结构，最后才考虑借代码

优先顺序：

1. 借方法论
2. 借工作流结构
3. 借领域模型和 contract
4. 最后才考虑借少量代码

### 2.2 借边界，不借包袱

我们主要借的是：

- 阶段边界
- 领域划分
- 工作流结构
- 关键数据关系
- 任务与 adapter 模式

我们不借的是：

- 原仓库历史兼容逻辑
- 高耦合 UI 结构
- 临时脚本式补丁
- 与原项目绑定的内容模板

### 2.3 代码复用必须是例外而不是默认

默认策略：

- 重新实现

只有满足以下全部条件时才允许考虑代码级复用：

- License 明确允许
- 复用范围足够小且可隔离
- 不引入原项目的运行时耦合
- 不引入隐式状态模型
- 不引入原项目的内容资产版权风险

## 3. 参考项目采用策略

### 3.1 drama-skills

#### 借什么

- creator-first 工作流
- 先确认后生产
- 五份核心真相源思路
- 审查和修订应作为正式阶段存在

#### 不借什么

- 纯 Skill/Markdown 驱动的运行形态
- 直接把产品做成命令式脚本集合
- 原项目的命名、提示词文本、示例项目内容

#### 对应到我们方案哪一层

- `PRD` 中的核心工作流
- `Architecture` 中的事实层设计
- `Data` 中的故事 / 设定 / 分镜 / prompt 文档分层

#### 采用结论

- `强采用方法`
- `中采用结构`
- `弱采用代码`

### 3.2 short-drama

#### 借什么

- 题材模板思路
- 钩子、节奏、反派层级、质量审查框架
- 故事规则引擎的产品定位

#### 不借什么

- 具体题材配方文本
- 具体案例内容
- 直接复制其剧情模板库和审查文案

#### 对应到我们方案哪一层

- `Story Engine`
- `Review Rules`
- `故事开发页`

#### 采用结论

- `强采用规则抽象`
- `禁止整包复制内容模板`

### 3.3 CineGen-ShortDrama

#### 借什么

- Script -> Asset -> Keyframe -> Video 主链路
- 导演工作台思路
- 关键帧作为图像与视频之间的桥梁
- continuity 显式建模

#### 不借什么

- 前端直连模型的实现风格
- 交互层承担过多业务状态的设计
- 原项目 UI 结构和具体实现细节

#### 对应到我们方案哪一层

- `Storyboard Studio`
- `KeyframeSpec`
- `ContinuityAnchor`
- `Prompt Compiler` 的输入结构

#### 采用结论

- `强采用工作流骨架`
- `重写实现`

### 3.4 huobao-drama

#### 借什么

- 多模型 adapter 思路
- 任务编排
- 媒体处理与导出能力
- 产物回填思路

#### 不借什么

- “从一句话直接到成片”的大一统耦合产品形态
- 直接复用其整套服务结构
- 直接照搬其配置体系、页面结构和执行逻辑

#### 对应到我们方案哪一层

- `Model Adapters`
- `Job Orchestrator`
- `Artifact Service`
- `Export Center`

#### 采用结论

- `强采用执行底座思想`
- `重写任务与适配 contract`

### 3.5 trae_projects

#### 借什么

- provider registry 思路
- adapter 分层思路
- 多模型统一调用的组织方式

#### 不借什么

- 双源状态
- 多处拼 prompt
- 巨型 service
- 运行状态与业务真相混存
- Vite/Electron 双套同构逻辑

#### 对应到我们方案哪一层

- `Model Profile`
- `Model Adapters`
- `Job Runner`

#### 采用结论

- `仅参考调用风格`
- `不继承结构`

## 4. 禁止直接复制的内容

### 4.1 禁止直接复制代码的区域

- 核心业务 service
- 状态管理器
- prompt 拼接模块
- 页面级业务逻辑
- 与模型绑定的执行链

### 4.2 禁止直接复制的内容资产

- 题材模板原文
- 故事案例
- 角色设定样例
- 示例 prompt
- 示例项目素材

### 4.3 禁止直接复制的产品壳

- 原项目页面结构
- 原项目交互路径
- 原项目命令系统
- 原项目的配置命名体系

## 5. 代码级复用准入规则

满足以下条件才可评估复用：

- 已确认准确仓库与 License
- 复用对象为小范围、通用型工具代码
- 可单独抽离，不依赖原项目上下文
- 不包含原项目业务常量和内容资产
- 不改变当前平台的事实层 / 执行层边界

允许评估的对象示例：

- 小型纯函数
- 与 provider 无关的解析工具
- 明确可隔离的 adapter helper

默认不建议复用的对象：

- prompt builder
- 业务 service
- 页面组件
- 状态管理器
- 数据同步逻辑

## 6. License 与商业化注意事项

### 6.1 当前原则

- 未明确核验 License 前，不做代码级复用决策。
- 即使 License 宽松，也不等于可以直接复制内容资产。
- 规则库、模板文本、案例和素材仍然可能属于更高风险区域。

### 6.2 实务要求

- 每个外部仓库如果进入“代码参考”阶段，必须单独做一次 License 核验。
- 每个计划复用的文件、模块、函数都必须记录来源。
- 商业化前必须再做一次第三方依赖和内容资产审查。

## 7. 对当前文档体系的影响

该采用策略会直接约束：

- `prd-v1.md`
  - 参考来源只表达方法和结构来源
- `architecture-v1.md`
  - 明确禁止 UI 拼 prompt、worker 回写真相、adapter 注入业务规则
- `data-and-api-v1.md`
  - contract 来源于抽象，而不是外部仓库原型复制

## 8. 一句话结论

- 我们的策略是：`参考外部项目的工作流、边界和抽象，但默认重写实现，不直接拼装它们的代码与内容资产。`
